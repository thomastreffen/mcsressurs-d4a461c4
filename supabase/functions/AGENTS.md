- Tripletex calls run only in edge functions via a `tripletex_connections` row (per company+environment, secret by name, Tripletex company verified, mode off/read_only/write_enabled) and `_shared/tripletex-guard.ts`; links are trigger-checked against their connection. Why: no company's data can reach another company's Tripletex.
- Stable Tripletex IDs live in `tripletex_links` (environment + Tripletex company + internal Tripletex id; number/name only as snapshot); a pending row is reserved before any create and partial unique indexes block duplicates. Legacy `tripletex_project_mappings`/`external_tripletex_id` are left untouched until migration. Why: idempotent, environment-separated mapping that never confuses numbers with IDs.
- Tripletex employee links key on canonical `people.id` (mcs_entity_type='employee'), resolved from a resource-plan assignee via `technicians.user_id -> user_accounts.auth_user_id (unique) -> person_id` in `resolveAssigneeIdentity`; a shared technician/people UUID is never trusted alone, names/e-mail never; unresolved -> `employee_identity_unresolved`, no network. Participant writes resolve job -> financial project (self or `parent_project_id`). Why: technicians.id differs from people.id for some staff.
- Tripletex is master for a linked financial project's open/closed status (`Project.isClosed`); participant writes require a freshly read `isClosed === false`, and read errors/missing field fail closed (`project_status_unknown`). Why: closed/invoiced projects must never get new participants from Hub.
- Future normal flow is Tripletex-first: economic projects are created in Tripletex and imported into Hub via `tripletex-import` (read-only to Tripletex; atomic `tripletex_import_project_shell` RPC creates one financial_project + active link keyed on stable Tripletex project ID, link_source `imported_from_tripletex`). Hub -> Tripletex create in `tripletex-project` is an explicit admin reserve only. Why: Tripletex is economic master.
- Only Hub projects with an explicit active project link take part in Tripletex; unlinked/legacy Hub projects stay Hub-only and are never auto-matched, backfilled or synced. Jobs/service/work packages under a financial project never become Tripletex projects. Why: no retroactive surprises in production.
- Tripletex owns the financial project number series; Hub never computes, reserves, suggests or guesses a "next project number" and has no editable number field in normal create (any manual override must be a separate explicit admin function). A future Hub -> Tripletex reserve create sends no number by default and reads back + stores the Tripletex-assigned number with the stable project ID; verify in TEST/OpenAPI that POST /project auto-assigns without `number` before building it, and never fall back to a local series without a new explicit decision. Why: avoid races with projects created directly in Tripletex; number is display/search only, ID is the mapping key.

## Visible project reference (TPX-F4.1)
- The Tripletex project number is the primary visible operational/business reference for financial projects and their Hub child jobs (header, job page, resource plan cards as `<nr> · <job title>`). Why: technicians, suppliers and material orders use it.
- Stable Tripletex internal ID (`tripletex_links.tripletex_id`) remains the technical mapping key; internal Hub job IDs (JOB-xxxx) are secondary only.
- Primary visible Tripletex project number applies only when the source financial project has an active Tripletex project-link in the same company; unlinked legacy projects (and their children) remain on fallback display. Resolved server-side by `get_visible_project_numbers` (invoker, events RLS) + `has_active_tripletex_project_link` (definer, returns only a boolean), so users need no tripletex_links access.
- The number is resolved for display via `src/lib/project-reference.ts` (own `financial_project` or same-company `parent_project_id` parent), never copied into titles and never used as unique job identity. Jobs without a financial parent keep legacy display; no number is invented.

## Resource-plan project selection (TPX-F4.2)
- For companies with an active configured connection, Tripletex is the economic project master and owns project numbers. Resource-plan `Prosjekt -> Eksisterende` searches all eligible same-company Hub parents (`search_resource_plan_projects`, invoker + definer link helpers), with Tripletex TEST on demand added only for an active TEST connection and super_admin. Only linked rows dedupe on stable Tripletex project ID; unlinked Hub rows never match on number/name.
- Tripletex-only selection imports/links via the canonical F4 `tripletex-import` preview/import flow (explicit customer confirmation, idempotent shell) before child work is created; new child jobs under a linked parent require a fresh `isClosed === false` (`project_open_status`, caller RLS + same company), failing closed.
- Active stable project link is the integration allow-list; never retro-auto-match legacy Hub rows on number/name.
- Project search pages eligible TEST projects before shared local separator/token matching and ranking; literal API name filters must not exclude variants or cross-field tokens. Discovery normalization never changes stable-ID mapping/import confirmation. Why: Test1/Test 1 must both be searchable.
- Tripletex project-link controls integration behavior, not resource-plan eligibility. Existing Hub projects remain plan-able whether linked or unlinked. Tripletex-first root-project creation rules apply only to companies with an active Tripletex connection configured for that company. Hub-only companies retain the existing root create flow; integrated companies block Hub root economic creation until an explicit Hub->Tripletex auto-number flow is verified and approved.
- Before child planning, `resource_plan_parent_context` checks caller RLS and selected company independently of display numbers. Only an active project-link requires a fresh Tripletex open-status read; unlinked parents make no Tripletex call. Why: linking is an integration allow-list, not a planning prerequisite.

- ms-calendar/tripletex-import/create-approval verify JWTs with SDK getClaims; server permissions/roles and caller-bearer RLS remain authoritative. Approval authentication uses the shared approval-auth verifier. Why: signing-key validation must not depend on a redundant Auth user fetch.
