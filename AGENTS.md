- New Planning files go in private bucket `planning-files` (path `{projectId}/...`) opened via short-lived signed URLs; legacy `planning/...` paths stay in public `job-attachments`. Why: real access control without breaking old links.
- DLE exports use company-scoped authenticated source queries and preserve original files via signed URLs; email uses inspection-response-send with frozen manifest and package-scoped private dle-exports objects, authorizing HMS edit server-side and logging recipients/versions/link expiry. Why: independent delivery without widened access or exposing other files.
- Standalone documentation exports use hms_document_exports with owner-scoped private files and reuse inspection-response-send without fabricating inspection IDs; content-specific module checks remain independent. Why: one delivery engine and company-scoped history without coupling general exports to inspections.
- InspectionExportTab reuses documentation delivery and finding evidence, and requires the active company to match the inspection before loading or exporting. Why: inspection-wide access must never mix documents from a different selected company.
- Planning staffing/date-deviation is derived live from events/event_technicians via `get_planning_wp_staffing`, never stored. Why: Ressursplan is source of truth.
- RLS checks that test "no row exists" in another RLS-protected table must use a SECURITY DEFINER helper. Why: RLS hides rows and inverts the check.
- Employment (employment_profiles, one is_primary per person) and system access are separate; cross-company access goes only through company_module_access + has_company_access(uid, company, module, level). Why: membership must never imply employment or blanket access.
- Company-module UI access uses the server-returned my_company_module_access matrix and CompanyModuleGate before mounting protected content; personnel for ResourcePlan uses resource_plan_personnel. Why: global roles and cached company selection must not widen module access or expose HR fields.
- On `hms`/`compliance`/finance-gated tables, `phase2_module_view/insert/update/delete` are RESTRICTIVE policies that AND with every permissive SELECT policy on that table. Why: a new permissive self-service policy (own rows, published content, "any active company member") is silently vetoed unless the matching restrictive policy is widened (`ALTER POLICY ... USING (existing OR self_service_condition)`) too — always check `pg_policy.polpermissive` before adding a carve-out.
- Self-service HMS pages (`/hms/handbok`, `/hms/mine-kjemikalier`, `/hms/klar-for-arbeid`) skip `HmsContextGate`/`CompanyModuleGate` entirely (see `HmsSelfServicePage` in `App.tsx`) and rely only on RLS (own rows, or "active member of company" for shared catalogs like chemicals/published handbooks). Why: these must stay open to every employee regardless of the hms.view/hms.manage company-module grant, which is an admin-only gate.
- AuthProvider keeps the same `user` object for the same person across Supabase SIGNED_IN/TOKEN_REFRESHED re-emits (fired on every tab return); providers key on `user.id` and only show loading for a new person/company context. Why: re-creating the user on tab focus remounted the shell and redirected guarded pages.
- LocalExportMenu receives explicit visible-row projections and frozen filter snapshots from each view; local exports reuse private documentation delivery with immutable source-module/company/owner scope and server-side view-level authorization. Why: exports must not query additional data or require unrelated HMS rights.
- Technician schedule emails use the shared job-time formatter with explicit Europe/Oslo and assignment overrides; database timestamps remain UTC instants. Why: server locale does not choose a timezone, and DST offsets must never be hardcoded.
- `events.entity_type` (financial_project/job/service/internal) is the economic classification; `project_type` stays the Resource Plan display type. Only financial_project may carry Tripletex links (DB triggers enforce). Why: avoid mirroring operative jobs as Tripletex projects.
- Subdirectories have their own `AGENTS.md` (e.g. `supabase/functions/` for Tripletex); read it before changing files there.
- Tripletex project-link controls integration behavior, not resource-plan eligibility. Existing Hub projects remain plan-able whether linked or unlinked. Tripletex-first root-project creation rules apply only to companies with an active Tripletex connection configured for that company. Why: additive integration must never block Hub-only dispatching.
- Resource-plan project search and company integration context use caller-scoped RPCs; link presence for saving is checked independently of visible project numbers and an unreadable or cross-company parent is rejected. Why: a missing display number must neither trigger Tripletex for Hub-only work nor bypass a linked project's open-status guard.
